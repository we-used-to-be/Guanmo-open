## 1. 真实用户空闲时自动补齐（优先执行）

- [ ] 在独立 Windows 桌面实例和匿名临时库创建无向量记忆，用强检索零词法问题触发生产队列；保留真实 `idleScheduler`，不替换调度器、不手动调用排队闭包。
- [ ] 验证持续交互时延后、真实空闲后自动执行、已取消请求不继续补齐；记录入队、准入、执行和持久化时间，以及实际批量/查询调用数。
- [ ] 再次查询确认可复用向量、事实未被改写、同模型同内容不重复生成；更新证据与结论。

通过标准：首次请求不等待记忆向量生成；强检索兜底输入最多 40 条、单次生成最多 8 条；真实空闲后缓存可用；取消不产生迟到注入。资源不足等环境条件须单独记录，不以跳过任务代替 PASS。

## 2. 实际 Token 与费用核对（等待账单配合）

- [ ] 确定独立测试时段和时区，在同模型、同匿名样例下分别记录旧/新请求；采集供应商返回的 `usage`、请求时间、模型、可用的 request ID、输入/输出/缓存 Token、Embedding Token、失败与重试次数。未返回用量记为缺失，不能记为 0。
- [ ] 用户提供该时段的脱敏用量/账单导出或截图，以及对应计价、缓存折扣、免费额度等信息；对齐两个供应商的时区和账单粒度，排除其他业务调用。
- [ ] 分别比较普通问答、记忆问答、后台补齐的每轮与每次检索用量及费用；保留预检索和 Agent 再次查询的全部调用，解释不能归因的差额。

通过标准：普通问答没有新增记忆调用/注入；记忆路径的实际调用与 Token 差异可解释，费用能按账单当期规则核对。只有汇总账单、缺失 usage 或混有其他业务且无法拆分时，保持待核对；输入字符数不代替 Token 或金额。

用户配合材料：测试日期和时间范围、账单时区、模型和接口类型、请求数、Token 分类、金额/单价及额度规则。可遮盖账号、余额、无关消费；无需提供 API Key、密码或真实聊天全文。不要将原始私人账单提交到公开仓库。

## 3. 新鲜 Release 同环境性能对照（发布前完成）

- [ ] 从固定旧/新版本分别构建可辨识的 Windows Release 产物；记录版本/产物哈希、WebView2、机器负载、模型与服务状态，使用独立数据目录。执行前记录延迟预算和采样计划。
- [ ] 同机交替测试普通问答、少量记忆和额外 5000 条记忆，区分冷/热缓存；分别记录本地检索、查询 Embedding、发送到真实可见模型文本、完整回答完成时间、调用数及结果正确性，报告中位数、P90、最大值与失败次数。
- [ ] 按项目性能约束，对编辑和预览各做旧/新至少 10 次冷启动对照；区分原生/WebView、真实 surface 与 appReady 指标，不将它们混作聊天首 Token。
- [ ] 与预先记录的预算核对，结合正确性和用量给出性能结论；环境异常、构建失败或样本不足单列，并补发布流程要求的验证。

通过标准：普通问答无新增记忆请求；各场景延迟满足明确预算且功能回归通过。预算未明确时只报告差值，不判性能达标；不把模型前言、最终答案、占位文字或开发态数据混用。

构建性能产物不代表创建新版本或发布。涉及版本号、tag、推送或 Release 时，执行 `docs/release-preflight.md` 与 `docs/push-safety.md` 的门禁和确认流程。

## 4. 隐含历史问法的路由与语义排序（独立改进项）

- [ ] 建立独立标注集，包含“有相关偏好”“有明确决策原因”“未保存原因”“完全无关”，区分未触发检索、候选漏召回、排序/阈值淘汰和回答越过证据。
- [ ] 固定旧/新路由、模型和样例，分别评估触发率、Recall、Precision、耗时及额外调用；校准集与留出集分开，不能只针对原句调阈值。
- [ ] 根据证据选择最小改动；现有同一次轻模型分类能否复用，应先评估。查询改写或额外重排模型须先证明收益及延迟/费用可接受，再确定实施范围。

通过标准：有充分依据时能检索支持事实，缺少因果证据时明确未知，不将“重视低资源占用”直接表述为“当年拒绝后台任务的已记录原因”。收益不足时保留现状和限制，不盲目降低阈值或扩大系统重构。

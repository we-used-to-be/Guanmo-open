# 长期记忆写入与召回时机优化计划

日期：2026-10-29。基线：`feature/agent-router-v2`，`1c84c40`。
状态：本文件保留最初规划；后续已进入实现，当前进度以 `docs/memory/AI_IMPLEMENTATION_PLAN.md` 为准，不代表桌面或真实模型已验收。用户现已明确：非敏感稳定事实自动生效，冲突和敏感信息仍需确认；下文最初的全部候选确认策略已被此选择取代。

## 目标与边界

让稳定事实更及时成为可确认候选，让已确认记忆在需要时被召回，同时减少重复提取、回答等待和无关注入。

- 继续使用 SQLite、现有候选确认与行动确认卡；候选不参与回答，只有确认后才生效。
- 保留 Router V2 规则快路和一次语义兜底；不为每条消息增加模型判断。
- 当前对话可解决的指代优先使用对话上下文，跨会话稳定事实才使用长期记忆。
- 首期不改 schema、不增加依赖、不重做 RAG、不合并 MCP、不在启动路径预热。
- 不自动读取真实用户数据库，不批量提取旧聊天，不清理或重建用户记忆。

## 源码核实的现状

| `src/services/memory/memoryPolicy.ts` | 正则过滤稳定事实信号，严格拒绝临时任务与待处理文本 | 保留保守准入，改进否定、纠正和混合表达，不能简单扩大关键词 |

| `src/services/agent/semanticRouter.ts` | 隐含历史依赖的语义触发受“是否存在任意对话”约束 | 存在历史不等于历史包含答案，需区分当前指代与长期依赖 |

| `src/services/actionProposalCommand.ts` | 显式保存确认时读取当时的主工作区 | 提案生成与确认之间切换工作区时，需重新核验原作用域 |

现有候选合并、事实替代、锁定保护、原子确认和 active 注入规则均应复用。以上为静态核实，不将潜在竞态报告为已复现故障。

## 建议时机

| 场景 | 写入时机 | 召回时机 |
| --- | --- | --- |
| “记住：以后用中文” | 优先形成现有确认卡；用户确认后写 active，不再并行生成相同自动候选 | 当前轮直接遵循用户指令；之后相关请求可读取已确认指令 |
| “我习惯先看结论” | 用户消息被本轮接受后记录候选任务；回答完成后闲时提取，仍须确认 | 回答确实涉及用户表达习惯时轻量读取 |
| “以后改用英文” | 形成替代候选；确认前不失效旧事实 | 本轮明确指令优先；确认后只返回新事实 |
| “按我的风格润色” | 待改写正文不参与提取 | 回答前检索 preference/instruction，最多 3 条 |
| “还记得我的项目约定吗” | 不因查询自身触发重复写入 | 回答前强检索，最多 10 条；失败、无结果分别表达 |
| 通用问答、普通翻译、一次性要求 | 不提取待处理内容 | 不额外检索；普通 Direct 不增加网络请求 |

普通候选仍在回答后处理是首期更简单的方案：先解决重复与异步归属，不立即让提取请求和主回答争抢模型连接。后续只有实测候选等待不可接受时，再尝试首个有效输出后启动；必须比较首字延迟和成本后决定。

## 分阶段实施

### 第一阶段：写入归属与重复控制

允许范围：`useAiChat.ts`、`memoryPolicy.ts`、`memoryService.ts`、现有行动提案链路。

1. 接受消息时固定 message/request/session ID、可见用户文本和规范化 workspace scope；不能在任务完成时重新读取“最新消息”或当前工作区。
2. 显式保存走确认卡；有明确保存提案的同一事实不再走自动候选。不要仅凭意图提前跳过但又未生成提案，造成漏记。
3. 自动候选在成功回答后的闲时串行处理；同一消息重试、重新生成不重复提交。新消息不能覆盖旧任务的文本或作用域。
4. 切会话、停止、删除来源、关闭应用的任务失效规则需明确；首期不保证退出后继续提取，不引入持久队列。失效任务不得迟到写入或重新创建被删除记忆。
5. 提取只发纯用户原文；已有记忆只读取全局与当前项目的必要元数据及有限相关条目，不加载 embedding，也不把别的项目记忆送入提取提示词。
6. 显式保存的查重先约束 scope，再按结构化身份/相似度匹配；新提案固定来源 scope，确认时工作区已变则提示重新确认，旧提案缺字段保持兼容但不能猜测项目归属。

验收：显式请求只出现一条对应保存路径；重新生成不增殖；否定“别记住”不写入；跨项目、快速切会话和删除来源后无迟到污染。

### 第二阶段：召回准入与单轮复用

允许范围：现有 Router V2、`useAiChat.ts`、`memoryService.ts`、`agent/tools.ts`。

1. 明确查询走强检索；明确个性化输出走分类受限的轻检索；通用问题不检索。
2. 将“有任意对话”改为更准确的依赖判定：本轮指代可由近邻对话满足则不查；明确长期偏好/跨会话约定仍可查。规则先行，歧义复用现有一次语义分类，不新增独立记忆分类模型。
3. 预检索和 Agent 工具共享本轮结果，按 query/scope/category 区分；查询实质改变才允许再查。空结果也复用，失败不伪装成空结果。
4. scope/status/category 在 SQLite 下推，项目与全局合并后仍有相关性门槛；当前轮新指令优先于旧记忆。
5. 注入增加总文本预算，建议先以轻量约 600、强检索约 1500 tokens 作为待评测起点；先保留事实，证据只给短摘录，不把原始长消息无限带入上下文。

验收：普通 Direct 无新增请求；有旧聊天时依然能处理真正长期依赖；候选、禁用和被替代记录不注入；强检索失败可识别；同轮相同查询不重复请求。

### 第三阶段：向量准备与真实评测

1. 优先在用户确认记忆或修改 active 内容后闲时生成向量；失败保留事实和词法回退，不能阻塞确认保存。
2. 回答前优先复用有效向量；限制查询向量耗时，缺失候选向量不再连续现场补算，后续闲时补齐。查询词法无交集时的漏召回单独评测，首期不扫描全库向量。
3. 向量回写仅更新缓存字段，并核对记录仍 active、内容 hash/模型未变；不得用旧完整对象 upsert，避免覆盖并发编辑或复活删除项。需要 Rust 命令时单独完成接口与兼容评审。
4. 仅保留匿名原因、耗时、命中数量和状态用于评估，不记录记忆原文、路径或凭据。

先用匿名固定用例建立当前分支基线，再对照修改结果：显式保存、否定、重复、偏好纠正、普通翻译、个性化改写、近邻指代、跨会话约定、跨项目隔离、无命中、网络失败、取消及迟到回写。

- 隔离/确认/删除不变量：固定用例全部通过。
- 精度与召回：人工标注“应查/不应查、应命中的事实”，分别报告误触发、漏召回和无关注入；不能把模型 confidence 当准确率。
- 性能：同机比较普通问答首字延迟、记忆检索 P50/P90、候选生成等待和请求数；阈值在基线后确定，不承诺尚未测量的收益。
- 定向检查优先复用 `npm run test:memory`、`npm run test:memory-query`，再跑实际受影响的 Router/异步用例及必要类型/Lint；不默认全量回归。
- Windows 桌面需实测保存确认、关开设置、重启后可召回、切工作区、纠正替代、删除及断网降级。真实模型单独验收。
